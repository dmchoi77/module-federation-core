# shared

`shared` 설정은 consumer와 producer 사이에서 공통 의존성을 공유할 때 사용합니다. 런타임에서 내려받는 양을 줄여 성능을 개선할 수 있고, 의존성 버전을 어떤 규칙으로 재사용할지도 정의할 수 있습니다. `shared`가 필요한 상황과 사용 방법은 [FAQ](#faq)에서 더 자세히 확인할 수 있습니다.

- 타입: `PluginSharedOptions`
- 필수: 아니요
- 기본값: `undefined`

`PluginSharedOptions` 타입은 다음과 같습니다.

```tsx
type PluginSharedOptions = string[] | SharedObject;

interface SharedObject {
  [sharedName: string]: SharedConfig;
}

interface SharedConfig {
  singleton?: boolean;
  requiredVersion?: string;
  eager?: boolean;
  shareScope?: string;
  import?: string | false;
  shareKey?: string;
  request?: string;
  allowNodeModulesSuffixMatch?: boolean;
  treeShaking?: TreeShakingConfig;
}

interface TreeShakingConfig {
  mode: 'server-calc' | 'runtime-infer';
  usedExports?: string[];
}

```

## 예제

```ts
new ModuleFederationPlugin({
  name: '@demo/host',
  shared: {
    react: {
      singleton: true,
    },
    'react-dom': {
      singleton: true,
    },
  },
  //...
});
```

## singleton

- 타입: `boolean`
- 필수: 아니요
- 기본값: `false`

shared scope 안에서 shared module의 버전을 하나만 허용할지 설정합니다. 이를 singleton 모드라고 합니다.

- `true`로 설정하면 singleton 모드가 활성화됩니다. `false`이면 활성화되지 않습니다.
- singleton 모드가 활성화되면 producer 컴포넌트와 consumer 사이의 shared dependencies는 한 번만 로드됩니다. 버전이 서로 다르면 더 높은 버전이 사용되며, 낮은 버전을 가진 쪽에는 warning이 출력됩니다.
- singleton 모드가 비활성화되어 있고 producer와 consumer의 shared dependency 버전이 다르면, 각 애플리케이션은 자기 의존성을 따로 로드합니다.

## requiredVersion

- 타입: `string`
- 필수: 아니요
- 기본값: `require('project/package.json')[devDeps | dep]['depName']`

필요한 버전을 지정합니다. 버전 범위도 사용할 수 있습니다. 기본값은 현재 애플리케이션의 의존성 버전입니다.

- shared dependencies를 사용할 때 의존성 버전이 `requiredVersion` 이상인지 확인합니다. 조건을 만족하면 정상적으로 사용합니다. 조건보다 낮으면 콘솔에 warning을 출력하고, shared dependencies 중 사용할 수 있는 가장 낮은 버전을 사용합니다.
- 한쪽은 `requiredVersion`을 설정하고 다른 쪽은 `singleton`을 설정한 경우, `requiredVersion` 쪽의 의존성이 로드됩니다. `singleton` 쪽은 자기 버전과 관계없이 `requiredVersion` 쪽 의존성을 그대로 사용합니다.

## eager

:::warning
`eager`를 true로 설정하면 shared dependencies가 entry file에 패키징되어 entry file 크기가 커질 수 있습니다. 주의해서 사용하세요.
:::

- 타입: `boolean`
- 필수: 아니요
- 기본값: `false`

shared module을 즉시 로드할지 설정합니다.

일반적으로는 lazy entry를 활성화한 뒤 필요한 시점에 shared modules를 비동기로 로드합니다. shared 기능은 사용하되 lazy entry를 켜고 싶지 않다면 `eager`를 `true`로 설정할 수 있습니다.

## shareScope

- 타입: `string`
- 필수: 아니요
- 기본값: `'default'`

Share scope 이름입니다. 기본값은 `'default'`입니다.

## import

- 타입: `string | false`
- 필수: 아니요
- 기본값: `undefined`

shared dependencies의 import 경로를 제어합니다. 기본값은 `undefined`입니다.

`false`로 설정하면 해당 shared dependency는 산출물에 포함되지 않고, consumer가 제공하는 `shared`만 사용합니다. 따라서 이 값을 설정하기 전에 consumer가 대응되는 `shared`를 제공하는지 확인해야 합니다.

## shareKey

- 타입: `string`
- 필수: 아니요
- 기본값: `shared` entry의 속성 이름(`key`)

런타임에서 Share Scope를 조회할 때 사용하는 key입니다. shared module이 정상적으로 협상되려면 producer와 consumer가 **같은** `shareKey`를 사용해야 합니다. 서로 다르면 각자 자기 복사본을 번들에 포함합니다.

기본값은 속성 이름 자체이므로 대부분의 경우 따로 설정하지 않아도 됩니다. 대표적인 사용 예시는 alias를 실제 패키지 이름에 매핑하는 경우입니다.

```ts
shared: {
  'my-alias': {
    import: 'react',      // resolve할 실제 package
    shareKey: 'react',    // Share Scope에서 "react"로 협상
  },
}
```

:::warning
`shareKey`를 생략하면 협상 key는 속성 이름 자체가 됩니다(위 예제에서는 `"my-alias"`). 다른 쪽이 `"react"`로 등록했다면 둘은 절대 match되지 않습니다.
:::

## request

- 타입: `string`
- 필수: 아니요
- 기본값: `shared` entry의 속성 이름(`key`)

빌드 시점에 번들러가 가로채는 모듈 request path입니다. 코드 안의 `import`가 이 값과 일치하면, 번들러는 해당 의존성을 산출물에 직접 번들링하지 않고 Share Scope consumer로 대체합니다.

기본값은 속성 이름이며 대부분의 경우 충분합니다. `request`와 `shareKey`의 차이는 다음과 같습니다.

| 필드 | 단계 | 답하는 질문 |
|---|---|---|
| `request` | 빌드 시점 · module graph | 어떤 `import`를 가로챌지 |
| `shareKey` | 런타임 · 협상 | Share Scope의 어떤 slot을 사용할지 |

### trailing slash를 사용한 접두사 매칭

`request`가 `/`로 끝나면 번들러는 이를 **접두사 매칭**으로 처리하고, 해당 네임스페이스 아래의 모든 서브패스 import를 가로챕니다. 최종 `shareKey`는 설정한 `shareKey`에 서브패스 suffix를 붙여 만듭니다. `shareKey`를 생략했다면 prefix 자체를 기준으로 사용합니다.

```ts
shared: {
  'react-dom/': {
    request: 'react-dom/',   // intercepts import 'react-dom/client', 'react-dom/server', etc.
    shareKey: 'react-dom/',  // 최종 shareKey = "react-dom/" + subpath suffix
  },
}
```

`lodash` 같은 utility library에도 같은 패턴을 사용할 수 있습니다.

```ts
shared: {
  'lodash/': {
    request: 'lodash/',    // intercepts import 'lodash/debounce', 'lodash/get', etc.
    shareKey: 'lodash/',   // 최종 shareKey = "lodash/" + subpath suffix
  },
}
```

`react-dom/client`, `lodash/debounce`, `@scope/package/subpath`처럼 subpath modules를 노출하는 패키지에는 이 설정이 중요합니다. 끝의 `/`가 없으면 정확히 일치하는 패키지 이름만 가로채며, subpath imports는 로컬에 번들링되고 shared scope 협상에 참여하지 않습니다.

:::warning 흔한 실수
`'react-dom'`처럼 끝의 `/` 없이 작성하면 `import 'react-dom'`만 가로챕니다.

`import { createRoot } from 'react-dom/client'`를 사용하는 코드는 React DOM의 두 번째 복사본을 로드하게 됩니다. 이는 React singleton 요구사항을 깨고 hydration error를 일으킬 수 있습니다. 자세한 내용은 [문제 해결 FAQ](/guide/troubleshooting/runtime.html#subpath-imports-are-not-shared-duplicate-dependency-loaded)를 참고하세요.
:::

## allowNodeModulesSuffixMatch

- 타입: `boolean`
- 필수: 아니요
- 기본값: `false`

resolve된 경로에서 `node_modules/` 뒤에 오는 부분을 기준으로 shared modules를 매칭하는 fallback lookup을 활성화합니다. consumer와 producer가 같은 패키지를 서로 다른 절대 경로로 resolve하지만, 그래도 같은 shared module로 취급하고 싶을 때 사용합니다. pnpm hoisting, symlink, 커스텀 번들러 loader 때문에 이런 상황이 생길 수 있습니다.

> 이전에는 이 옵션을 `nodeModulesReconstructedLookup`이라고 불렀습니다.


## treeShaking

- 타입: `TreeShakingConfig`
- 필수: 아니요
- 기본값: `undefined`

shared dependencies의 tree-shaking 동작을 설정합니다. shared dependencies에 tree shaking을 활성화하면 shared bundle 크기를 줄일 수 있습니다.

> 이 기능에는 Rspack 사용을 권장하며, 문서와 예제도 Rspack 사용을 우선합니다.


### usedExports

- 타입: `string[]`
- 필수: 아니요
- 기본값: `undefined`

shared dependency에서 사용하는 export를 수동으로 **추가**합니다.

### mode

- 타입: `'server-calc' | 'runtime-infer'`
- 필수: 아니요
- 기본값: `undefined`

Tree-shaken shared dependencies의 로딩 전략을 설정합니다.

- `runtime-infer`: consumer의 `usedExports`를 기준으로 추론합니다. provider의 `usedExports`가 consumer의 `usedExports`를 만족하면 provider의 `shared`를 사용하고, 그렇지 않으면 consumer 자신의 `shared`를 사용합니다. 둘 다 조건을 만족하지 못하면 전체 번들로 fallback합니다.
- `server-calc`: 서버가 전달한 Snapshot을 기준으로 shared dependency를 로드할지 결정합니다.

### filename

- 타입: `string`
- 필수: 아니요
- 기본값: `undefined`

Tree-shaken shared module의 출력 파일 이름을 지정합니다.

## FAQ

### When to use shared dependencies

프로젝트 사이에서 모듈을 소비하다 보면 **의존성 중복 로딩**이나 **singleton 제약** 같은 문제가 자주 생깁니다. 이런 문제는 `shared`를 설정해 해결할 수 있습니다.

- Producer가 제공하는 모듈에서 사용하는 서드파티 패키지가 consumer에서도 널리 사용되는 경우. 예: `lodash.get`
- Producer가 제공하는 모듈에서 사용하는 서드파티 패키지에 singleton 요구사항이 있는 경우. 예: `react`
- Producer가 제공하는 모듈에서 사용하는 서드파티 패키지가 consumer에서도 사용되고, 의존성 크기가 크며, tree shaking을 지원하지 않는 경우. 예: on-demand 사용을 하지 않는 `lodash`
- Producer가 제공하는 모듈에서 사용하는 서드파티 패키지가 consumer에서도 사용되고, 의존성 크기가 크며, tree shaking을 지원하지만, 노출된 모듈을 모두 사용하는 경우. 예: `antd`

이런 경우 해당 의존성을 `shared` 설정에 추가할 수 있습니다.

### How to use shared dependencies

사용 사례에 따라 {props.brandName || props.name || 'Module Federation'}은 shared dependency 설정을 두 가지 형식으로 지원합니다. 일반적인 경우에는 array 형식이 적합하고, 세부 조정이 필요하다면 object 형식을 사용합니다.

**Array 형식(일반적인 경우)**

{props.brandName || props.name || 'Module Federation'} 빌드 설정의 `shared`에 해당 의존성을 추가하면 됩니다. 예시는 다음과 같습니다.

import ArrayShared from '@docs/_snippets/configure/array-shared';
import React from 'react';

{props.arrayShared || React.createElement(ArrayShared)}

**Object 형식(세부 설정이 필요한 경우)**

{props.brandName || props.name || 'Module Federation'}의 `shared` 설정에 shared dependencies를 추가합니다. `key`는 의존성 이름이고, `value`는 해당 의존성에 적용할 설정입니다.

import ObjectShared from '@docs/_snippets/configure/object-shared'

{props.objectShared || React.createElement(ObjectShared)}
