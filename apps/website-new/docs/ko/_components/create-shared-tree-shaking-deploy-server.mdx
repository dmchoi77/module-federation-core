## 배포 서버 (참고 구현)

자체 배포 서버를 구축한다면 아래 흐름을 참고해 `server-calc`를 구현할 수 있습니다.

### 1. 배포 중 `usedExports` 수집

CI/CD 배포 파이프라인에서 배포 서비스는 다음 작업을 수행해야 합니다.

- 곧 릴리스될 모든 애플리케이션의 빌드 메타데이터를 수집합니다. 보통 `mf-stats.json` 또는 비슷한 파일을 사용합니다.
- 같은 shared dependencies(예: `antd@6.1.0`)에 대해 각 애플리케이션이 선언한 `usedExports`를 모읍니다.

### 2. 전역 최소 합집합 계산

수집한 `usedExports` 목록을 병합하고 중복을 제거해, 시스템 전체에 필요한 최소 전역 집합(합집합)을 계산합니다.

### 3. 보조 빌드로 최적화된 shared bundle 생성

빌드 도구(예: Rspack CLI)를 독립 빌드로 실행하고 다음 값을 전달합니다.

- 대상 shared dependencies 이름과 버전(예: `antd@6.1.0`)
- 이전 단계에서 계산한 전역 `usedExports` 합집합

출력물은 필요한 모듈만 포함한 독립 shared bundle입니다.

### 4. Snapshot 업데이트 및 배포

최적화된 번들을 정적 asset 호스트(CDN)에 업로드합니다. 그런 다음 Module Federation Snapshot 파일(보통 remote의 `mf-manifest.json`)에 다음 필드를 업데이트합니다.

- `secondarySharedTreeShakingEntry`: 최적화된 번들의 URL
- `secondarySharedTreeShakingName`: 고유한 번들 이름
- `treeShakingStatus`: 사용 가능 상태 표시

마지막으로 업데이트된 Snapshot을 모든 consumer에 배포합니다.

### 5. 런타임 온디맨드 로딩

사용자가 애플리케이션에 접속하면 MF 런타임이 Snapshot을 읽습니다. `treeShakingStatus`가 사용 가능 상태이고 환경이 로딩 조건을 만족하면, 전체 번들 대신 `secondarySharedTreeShakingEntry`를 통해 최적화된 번들을 로드합니다.

:::tip 버전 관리, 캐싱, 호환성

- **엄격한 버전 관리**가 기본입니다. 불일치를 피하려면 보조 빌드와 런타임 로딩이 정확히 같은 버전(예: `antd@6.1.0`)을 기준으로 동작해야 합니다.
- 보조 빌드 산출물에는 **적절한 캐싱 전략**을 적용하세요. 전역 `usedExports`에 따라 내용이 달라지므로, 장기 캐싱에는 콘텐츠 해시 기반 파일명을 권장합니다.
- 이 흐름은 **이전 방식과 호환**됩니다. 기능을 활성화하지 않았거나 조건을 만족하지 않으면 consumer는 기존 기능에 영향 없이 전체 번들로 fallback합니다.

:::
