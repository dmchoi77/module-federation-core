# Angular 앱을 마이크로 프론트엔드로 나누기: 단계별 가이드
## 마이크로 프론트엔드 소개

마이크로 프론트엔드는 큰 애플리케이션을 작고 독립적인 단위로 나누어 관리하는 확장 가능한 방식입니다. 각 팀이 애플리케이션의 일부를 독립적으로 개발, 테스트, 배포할 수 있어 효율은 높이고 복잡도는 낮출 수 있습니다.

### 마이크로 프론트엔드란?

마이크로 프론트엔드는 마이크로서비스의 원칙을 프론트엔드 개발에 적용해 큰 애플리케이션을 관리 가능한 단위로 나누는 접근법입니다. 이렇게 나눈 단위, 즉 micro-app은 독립적으로 개발하고 라우팅 등을 통해 통합할 수 있습니다. Module Federation 관점의 마이크로 프론트엔드는 [module federation 문서](https://test.com)에서 더 자세히 다룹니다.

#### 관점

사용자에게는 하나의 통합된 애플리케이션처럼 보이지만, 개발자는 Module Federation 같은 방식을 활용해 micro-app을 더 유연하게 배포하고 서빙할 수 있습니다.

## 마이크로 프론트엔드 기술 지형

마이크로 프론트엔드를 사용하면 애플리케이션의 각 영역에 서로 다른 프레임워크나 라이브러리를 적용할 수 있습니다. 유연성이 커지는 만큼 팀 이동성 같은 새로운 과제도 생깁니다. Single SPA 같은 도구나 Angular용 Nx처럼 프레임워크에 특화된 솔루션은 여러 기술을 하나의 일관된 애플리케이션으로 통합하는 데 도움을 줍니다. 목표는 각 micro-app을 독립적으로 빌드, 테스트, 배포하면서도 사용자에게는 끊김 없는 경험을 제공하는 것입니다.

## 마이크로 프론트엔드 전환 다루기

### 큰 애플리케이션의 어려움

큰 애플리케이션은 테스트와 빌드 시간이 길어지고 로컬 서버 실행도 느려지기 쉽습니다. 애플리케이션을 더 작은 부분으로 나눠 마이크로 프론트엔드로 전환하면 이런 문제를 크게 줄일 수 있습니다.

마이크로 프론트엔드를 구현하는 방법은 다양하고, 관련 가이드와 자료도 많습니다. 어떤 자료는 처음부터 마이크로 프론트엔드를 만드는 데 집중하는데, 큰 규모로 성장할 새 프로젝트라면 이런 접근이 잘 맞습니다.

## 기존 애플리케이션 리팩터링

이 가이드에서는 Angular CLI로 만든 기존 애플리케이션을 공유 라이브러리와 개별 앱으로 나누는 리팩터링에 집중합니다. 분리한 요소들은 다시 큰 애플리케이션 안에 자연스럽게 통합되며, 사용자 경험은 하나로 유지하면서 개발 효율을 높일 수 있습니다.

## 마이크로 프론트엔드 적용을 위한 기본 애플리케이션 살펴보기

### 샘플 애플리케이션 준비

마이크로 프론트엔드를 살펴보기 위해 샘플 애플리케이션을 사용합니다. 이 애플리케이션은 크거나 복잡하지는 않지만, 마이크로 프론트엔드 아키텍처에서 각 micro-app과 통합될 수 있는 여러 서비스를 포함하고 있습니다.

#### 애플리케이션 구조

이 애플리케이션의 구조는 Angular CLI로 새 프로젝트를 만들었을 때 얻는 일반적인 구조와 비슷합니다. 주요 요소는 다음과 같습니다.

- **기능 모듈**: `add-user`, `dashboard`, `login`, `user-list`처럼 앱 안의 특정 기능이나 페이지를 담당합니다.
- **Models**: 앱에서 사용하는 데이터의 형태를 정의하는 자료 구조입니다.
- **공유 Services**: 인증(`auth`)이나 사용자 관리(`users`)처럼 애플리케이션의 여러 영역에서 함께 사용하는 공통 기능입니다.

디렉터리 구조는 다음과 같습니다.

```bash
- src
  + features
    - add-user
    - dashboard
    - login
    - user-list
  - models
  + shared
    - auth
    - users
```
### 리팩터링 전략

목표는 서비스와 모델을 micro-app 사이에서 공유할 수 있는 라이브러리로 리팩터링하는 것입니다. 반면 기능 모듈은 각각 독립 애플리케이션으로 전환합니다. 이렇게 하면 모듈성을 확보하고 각 기능을 독립적으로 개발, 배포하기 쉬워집니다.

#### 라우팅 고려사항

현재 애플리케이션의 라우팅은 lazy loading을 사용해 성능과 사용자 경험을 높입니다. 다음은 라우팅 전략의 일부입니다.

```typescript title="app-routing.module.ts"

import { NgModule } from '@angular/core';
import { RouterModule, Routes } from '@angular/router';
import { isLogged } from './shared/auth/is-logged.guard';
import { isNotLogged } from './shared/auth/is-not-logged.guard';

const routes: Routes = [
  {
    path: '',
    canMatch: [isLogged],
    loadChildren: () =>
      import('./features/dashboard/dashboard.module').then((m) => m.DashboardModule),
  },
  {
    path: '',
    canMatch: [isNotLogged],
    loadChildren: () => import('./features/login/login.module').then((m) => m.LoginModule),
  },
];

@NgModule({
  imports: [RouterModule.forRoot(routes)],
  exports: [RouterModule],
})
export class AppRoutingModule {}
```

이 라우팅 모듈은 `isLogged`, `isNotLogged` 같은 guard로 사용자 인증 상태에 따라 라우트 접근을 제어하고, dynamic import로 기능 모듈을 lazy loading하는 방식을 보여줍니다.

### 마이크로 프론트엔드 마이그레이션을 작게 시작하기

#### 복잡한 애플리케이션을 옮기는 접근법

복잡한 애플리케이션을 마이크로 프론트엔드 아키텍처로 옮기는 일은 쉽지 않습니다. 이 과정을 원활하게 진행하려면 명확한 단계와, 필요하다면 의존성 관리를 돕는 추가 도구가 필요합니다.

##### 먼저 의존성이 없는 파일부터

1. **독립 파일 식별**: 의존성은 없지만 여러 서비스와 기능 모듈에서 함께 사용하는 파일부터 찾습니다. 예를 들어 이 샘플 애플리케이션에서는 `models` 폴더가 여기에 해당합니다. 앱 전체에서 사용하는 model을 담고 있지만 다른 파일에는 의존하지 않습니다.

2. **해당 파일을 담을 새 라이브러리 생성**: Angular CLI로 이 독립 파일들을 담을 라이브러리를 생성합니다. 명령은 다음과 같습니다.

```bash
ng generate library models
```

이 명령은 다음 작업을 수행합니다.

- `models` 라이브러리를 포함하는 새 `projects` 폴더를 생성합니다.
- `ng-packagr`를 의존성으로 설치합니다.
- 새 라이브러리가 포함되도록 `angular.json`과 `tsconfig.json`을 업데이트합니다.

#### 라이브러리 커스터마이징

- **Path Mapping**: npm 모듈과 충돌할 가능성을 줄이려면 `tsconfig.json`의 path mapping을 수정합니다. npm 모듈 이름에는 `@@`를 사용할 수 없으므로, prefix로 `@@`를 쓰는 방식을 권장합니다.
- **패키지 이름**: Library를 registry에 publish할 계획이라면 `package.json`의 이름이 registry에서 사용할 수 있는 안전한 이름인지 확인하세요. 그렇지 않다면 편한 이름을 사용해도 됩니다.

#### Model 리팩터링

1. **Model 이동**: `models` 폴더의 내용을 새 라이브러리로 옮깁니다. 생성된 라이브러리에는 기본 컴포넌트, 모듈, 서비스가 들어 있는데 필요 없으면 제거해도 됩니다. user model 파일은 라이브러리의 `lib` 폴더 안에 둡니다.
2. **Public API 업데이트**: `public-api.ts` 파일을 수정해 `lib` 폴더의 적절한 내용을 export합니다.

#### 파일 이동 관리

- **Git으로 파일 이동하기**: 운영체제의 파일 이동 기능 대신 `git mv`를 사용하세요. Git이 변경 내역을 더 정확히 추적할 수 있습니다.

#### 라이브러리 폴더 구조

`models` 라이브러리의 폴더 구조는 이해하기 쉽고 접근하기 편하도록 정리해야 합니다.

#### Import 업데이트

**Import 경로 변경**: 기존 import 경로를 새 라이브러리 경로로 바꿉니다. 예를 들면 다음과 같습니다.

```javascript
// from
import { User } from 'src/app/models/user';
// to
import { User } from '@@models';
```

경로가 `tsconfig.json`에 지정한 값과 일치하는지 확인하세요.

#### 라이브러리 빌드

**오류 해결**: 처음에는 라이브러리가 아직 빌드되지 않아 오류가 발생할 수 있습니다. 다음 명령으로 해결합니다.

```bash
ng build models
```

이 명령은 `models` 라이브러리를 컴파일해 TypeScript가 `@@models`를 올바르게 참조할 수 있게 합니다.


#### 기본 단계를 넘어서는 마이그레이션

독립적인 코드를 라이브러리로 성공적으로 옮겼다면, 다음 단계는 분리할 수 있는 의존 코드로 넘어가는 것입니다. 이 예제에서는 guard를 포함한 `auth` service를 별도 라이브러리로 옮기는 데 집중합니다. 과정은 `models` 라이브러리에서 진행한 단계와 비슷합니다.

<Steps>

Angular CLI로 `auth` 라이브러리를 생성합니다.

여기까지 완료하면 애플리케이션의 일부가 라이브러리로 성공적으로 옮겨진 것입니다. 애플리케이션은 계속 동작하고, Angular가 전체 앱을 매번 다시 빌드하지 않아도 되므로 속도도 개선될 수 있습니다. 이제 컴포넌트, service, pipe 등 여러 요소를 공유해야 하는 큰 애플리케이션에 적합한 독립 테스트와 빌드 단위를 갖게 됩니다.

#### 더 복잡한 라이브러리 구성

더 복잡한 애플리케이션에서는 ng-packagr의 Secondary Entrypoints 기능을 사용해 컴포넌트나 service 같은 공통 항목을 그룹화할 수 있습니다. 이를 위해서는 추가 설정이 필요합니다.

### 첫 번째 애플리케이션 마이그레이션

라이브러리 패키징 방식을 살펴봤으니, 이제 기능 모듈을 독립 애플리케이션으로 옮겨 보겠습니다.

#### 마이그레이션할 모듈 선택

### 기능 모듈 리팩터링

1. **기능 모듈 이동**: 라이브러리에서처럼 파일을 대체하는 대신, 새 애플리케이션의 `src` 아래에 `feature` 폴더를 만들고 그 안으로 `login` 폴더를 옮깁니다.

2. **라우팅 업데이트**: `login` 애플리케이션의 `app-routing.module.ts`를 수정해 루트 라우트에서 `Login` 모듈을 제공하도록 합니다.

3. **AppComponent 조정**: 라우팅이 올바르게 동작하도록 `login` 앱의 `app.component.html`에 `<router-outlet></router-outlet>` 태그가 있는지 확인합니다.

### 스타일 처리

처음에는 새 애플리케이션에 스타일이 적용되지 않은 것처럼 보일 수 있습니다. 메인 애플리케이션의 `styles.scss` 파일을 새 애플리케이션으로 복사하면 해결됩니다. 애플리케이션 간 스타일 공유는 이후 문서에서 더 자세히 다룹니다.

### 결과

정상적으로 진행했다면 `login` 애플리케이션은 이제 독립적으로 실행되고, 스타일이 적용되며, 기능도 동작해야 합니다. 완성된 마이크로 프론트엔드 아키텍처로 가는 중요한 단계를 마친 셈입니다.

## Login 앱을 메인 애플리케이션에 통합하기

`Login` 애플리케이션을 독립 실행 가능한 형태로 설정했다면, 다음 중요한 단계는 이를 메인 애플리케이션과 통합하는 것입니다. `Login` 앱을 라이브러리로 빌드하고, 메인 모듈의 기존 lazy loading 기능을 사용해 가져옵니다.

### `angular.json` 업데이트

1. **프로젝트 설정 수정**: `angular.json`에서 라이브러리 설정 하나를 복제해 `login` 설정 아래에 배치합니다. key 이름을 `login-lib`로 바꾸고, `root`, `sourceRoot` 같은 참조가 `login` 애플리케이션을 가리키도록 업데이트합니다.

업데이트한 설정은 `login` 애플리케이션의 실제 경로와 설정에 맞게 조정해야 합니다.

2. **`ng-package.json` 생성**: 이 파일은 `ng-packagr`에 애플리케이션 패키징 방법을 알려주는 데 필요합니다. 다른 라이브러리의 기존 `ng-package.json`을 `Login` 애플리케이션 루트 폴더로 복사한 뒤, 빌드 출력 경로를 지정하도록 `dest` key를 `"../../dist/login-lib"`로 업데이트합니다.

### Public API 구성

1. **`public-api.ts` 생성**: 일반적인 라이브러리 구성과 달리 이 파일은 `src` 폴더 아래에 만듭니다. `Login` 기능 모듈만 export해야 합니다.
```javascript
// public-api.ts
export { LoginModule } from './app/feature/login/login.module';
```

### 라이브러리 빌드

1. **`package.json` 준비**: 다른 라이브러리의 `package.json`을 `Login` 애플리케이션 루트로 복사하고 프로젝트 이름을 수정합니다.
2. **빌드 명령 실행**: Angular CLI 빌드 명령을 실행합니다.
```bash
ng build login-lib
```

이 과정은 `Login` 모듈을 library로 컴파일합니다.

### 라이브러리 가져오기

1. **`tsconfig.json` 업데이트**: `tsconfig.json`에 `login-lib`의 새 path mapping을 추가하고 `"dist/login-lib"`를 가리키게 합니다. TypeScript가 라이브러리를 올바르게 찾으려면 꼭 필요한 단계입니다.

2. **애플리케이션 라우팅 수정**: `app-routing.module.ts`에서 lazy loading 경로가 새 라이브러리를 사용하도록 업데이트합니다.
```javascript
loadChildren: () => import('@@login').then((m) => m.LoginModule),
```

### 통합된 애플리케이션 실행

이 변경을 마치면 평소처럼 애플리케이션을 실행할 수 있습니다. 이제 별도 프로젝트가 된 `Login` 모듈이 메인 앱 안에서 자연스럽게 동작해야 합니다.

### 추가로 고려할 점

- **빌드 자동화**: 과정을 단순화하려면 Lerna 같은 도구로 빌드와 의존성 관리를 자동화하는 방안을 고려하세요. 여러 라이브러리와 애플리케이션을 다룰 때 특히 도움이 됩니다.
- **버전 관리**: 현재 구성은 라이브러리 버전 관리를 사용하지 않습니다. 호환성을 깨는 변경이 생기면 관리가 복잡해질 수 있으므로, 장기 유지보수를 위해 버전 관리 전략을 마련하는 것이 좋습니다.
