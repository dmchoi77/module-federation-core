# 모노레포에서 Module Federation을 사용할 때의 장점

Module Federation은 애플리케이션 사이에서 코드를 공유할 수 있게 해 주는 강력한 도구입니다. 더 모듈화되고 유지보수하기 쉽고 확장 가능한 애플리케이션을 만들 수 있습니다. 이 가이드에서는 모노레포에서 Module Federation을 사용할 때 얻을 수 있는 장점을 살펴봅니다.

폴리레포(polyrepo), 즉 여러 저장소를 나누어 운영하는 방식은 오랫동안 마이크로 프론트엔드 개발에서 사실상의 기본 선택지였습니다. 조직 구조상의 문제를 해결하기 위한 접근이었지만, 코드 공유, 의존성 관리, 버전 관리, 팀 자율성 측면에서는 또 다른 운영 부담을 만들기도 합니다.

마이크로 프론트엔드로 팀 자율성을 높이려는 시도는 자연스럽게 폴리레포 구조로 이어졌습니다. 각 팀이 자기 저장소를 소유하고 자기 코드베이스를 관리하는 방식입니다. 하지만 이 접근은 협업 부족, 투명성 저하 같은 문제도 함께 낳았습니다.

모노레포를 선택하면 여러 저장소를 관리하는 부담 없이 Module Federation의 장점을 활용할 수 있습니다. 여기에 코드 공유와 의존성 관리 측면의 추가적인 이점도 얻을 수 있습니다.
이 가이드는 모노레포에서 Module Federation을 사용할 때 어떤 장점이 있고, 그것이 조직 운영상의 문제를 어떻게 줄이는지 설명합니다.

## 폴리레포 접근의 잠재적 단점

팀 입장에서는 완전한 격리가 매력적으로 보일 수 있습니다. 하지만 Module Federation에서는 그만큼 주의할 점도 많습니다. Module Federation 시스템을 구성할 때 잊기 쉬운 사실이 하나 있습니다. 사용자가 최종적으로 경험하는 결과물은 하나의 애플리케이션이라는 점입니다.
따라서 하나의 애플리케이션을 구성하는 폴리레포들이 기술적 의사결정에서 완전히 분리되어 있으면, 최종 사용자 경험에 불일치가 생길 수 있습니다.

폴리레포 접근에서 자주 발생하는 다른 문제도 살펴보겠습니다.

### 피드백 루프

폴리레포 접근에서는 투명성과 피드백 루프가 부족해지기 쉽습니다. Module Federation 시스템에서는 특히 문제가 될 수 있습니다.

한 팀이 애플리케이션의 일부를 변경했을 때, 그 변경이 다른 부분에 어떤 영향을 줄지 파악하기 어렵습니다. 런타임 문제나 호환성을 깨는 변경은 배포가 끝난 뒤에야 드러나는 경우도 많습니다.

프로덕션에 도달하기 전에 변경이 안전한지 확인하는 QA 절차가 있더라도 피드백 루프가 느리면 팀의 흐름이 끊깁니다. 새 기능을 개발하기보다 변경을 롤백하거나 갑자기 발생한 문제를 급히 고쳐야 할 수 있습니다.

### 공유 코드 전략

폴리레포 사이에서 코드를 공유하는 것은 쉽지 않습니다. 보통 비공개 패키지 registry를 만들고 유지해야 합니다. 공유 코드는 빌드된 뒤 이 registry에 배포되고, 다른 폴리레포가 해당 패키지를 소비합니다. 공유 코드가 변경되면 registry에 새 버전을 릴리스해야 합니다.

이 과정은 시간이 오래 걸리고 실수도 발생하기 쉽습니다. 어떤 팀의 기능 작업이 공유 코드 PR의 릴리스에 의존한다면, registry 배포가 완료될 때까지 작업이 막힐 수도 있습니다.

이는 다시 피드백 루프 문제로 이어집니다. 팀은 registry가 업데이트되어야 변경의 영향을 확인할 수 있고, 팀이 격리되어 있다면 그 영향 자체를 보지 못할 수도 있습니다. 그 결과 다른 팀에 영향을 주는 호환성을 깨는 변경이 의도치 않게 들어갈 수 있습니다.

공유 코드를 소비하는 팀은 Module Federation 시스템 전체의 호환성을 유지하기 위해 사용하는 공유 패키지 버전을 계속 업데이트해야 합니다. 그렇지 않으면 런타임에서 호환성을 깨는 변경이 드러날 위험이 있습니다.

### 의존성 관리

폴리레포는 의존성 관리 문제도 만들 수 있습니다. 각 팀이 자기 저장소 안에서 격리되어 작업하면 서로 다른 의존성 또는 같은 의존성의 다른 버전을 사용할 수 있습니다. 이는 충돌, 버전 문제, 중복 의존성으로 인한 번들 크기 증가로 이어질 수 있습니다.

예를 들어 한 팀은 React 18을 사용하고 있는데 다른 팀이 React 19로 의존성을 올렸다고 가정해 보겠습니다. 이 변경이 프로덕션에 배포되면 호환되지 않는 코드와 런타임 오류가 발생할 위험이 큽니다. 애플리케이션의 다른 부분이 아직 React 19를 지원하지 않는다면 특히 그렇습니다.

폴리레포 환경에서는 React 19 업데이트가 다른 팀을 깨뜨릴 수 있다는 사실을 즉시 알려 주지 않습니다. 그 결과 불필요한 혼란과 롤백이 발생할 수 있습니다.

### 테스트 전략

팀이 서로 격리되어 일하면 테스트 전략이나 도구도 달라질 수 있습니다. 그러면 시스템 전체의 테스트 일관성이 떨어지고, 애플리케이션 품질에도 영향을 줍니다.

QA 과정도 더 어려워집니다. 각 마이크로 프론트엔드를 따로 테스트하거나, 모든 마이크로 프론트엔드를 함께 테스트해야 합니다.

개별 마이크로 프론트엔드만 테스트하면 애플리케이션 전체 품질을 충분히 보장하기 어렵습니다. 통합 지점이나 공유 컨텍스트가 함께 검증되지 않기 때문입니다.

또한 전체 애플리케이션의 일부 계층을 mock할 수 있는 테스트 프레임워크를 별도로 만들어야 할 수도 있습니다. 이 테스트 프레임워크가 애플리케이션의 다른 부분과 계속 맞춰지도록 유지하는 비용도 발생합니다.

전체 애플리케이션을 테스트하면 더 높은 신뢰도를 얻을 수 있습니다. 하지만 polyrepo에서는 각 마이크로 프론트엔드의 최신 버전을 배포할 수 있는 설정 가능한 테스트 환경을 따로 구성해야 합니다.
이는 시간이 오래 걸리고 클라우드 리소스 비용도 들며, 테스트 중 발견된 문제에 대한 피드백도 늦어져 전체 반복 속도를 떨어뜨립니다.

## 모노레포는 이런 문제를 어떻게 해결하나요?

모노레포는 프로젝트의 모든 코드를 하나의 저장소에 담는 구조입니다. 전체 프로젝트의 단일 기준점이 됩니다.
앞서 본 문제를 모노레포가 어떻게 줄일 수 있는지 하나씩 살펴보겠습니다.

### 피드백 루프

모노레포에서는 모든 코드가 같은 저장소에 있기 때문에 피드백 루프가 단순해집니다. 한 팀의 변경이 다른 팀과 마이크로 프론트엔드에 어떤 영향을 주는지 더 빠르게 확인할 수 있습니다. 수동 릴리스 과정이 줄어들고 호환성을 깨는 변경의 위험도 낮아집니다.

개발자는 변경을 만드는 시점에 영향 범위를 확인하고, 영향을 최소화하기 위한 조치를 바로 취할 수 있습니다.

### 공유 코드 전략

[Nx](https://nx.dev) 같은 모노레포 도구를 사용하면 중앙 패키지 registry 없이도 팀 간 코드를 공유할 수 있습니다. 팀이 registry에 변경을 수동으로 릴리스할 필요가 줄고, 충돌과 버전 문제의 위험도 낮아집니다.

공유 코드용 별도 저장소를 업데이트하고, 중앙 registry에 새 릴리스가 올라오길 기다리고, consumer에서 새 버전을 설치하는 과정이 줄어들기 때문에 개발 속도도 크게 개선됩니다.

공유 코드 변경과 그 코드를 소비하는 코드 변경을 같은 저장소에서 함께 만들 수 있습니다. 이는 팀 간 협업과 투명성을 높이고, 즉각적인 피드백을 통해 품질을 개선하며, 호환성을 깨는 변경의 위험을 줄입니다.

Dependency graph와 IDE 지원 덕분에 어떤 코드가 공유 코드를 사용하고 있는지도 더 잘 볼 수 있습니다. 개발자는 변경의 영향도를 더 근거 있게 판단할 수 있습니다.

### 의존성 관리

모노레포에서는 React나 Angular 같은 주요 의존성의 버전 업데이트를 모든 consumer에 한 번에 적용할 수 있습니다. 이를 통해 시스템 전체의 호환성을 높이고 호환성을 깨는 변경의 위험을 줄일 수 있습니다.

물론 이런 업그레이드는 팀 간 협업과 일정 조율이 필요합니다. 하지만 최종 사용자에게는 더 높은 안정성과 호환성으로 이어집니다.

팀은 필요하다면 `date-fns`나 `lodash`처럼 상대적으로 작은 의존성에 대해 각자의 버전을 사용할 수도 있습니다. 각 프로젝트의 `package.json`에 정의하거나 root `package.json`에서 alias를 설정하는 방식으로 조정할 수 있습니다.

### 테스트 전략

모노레포에서는 테스트 전략도 단순해집니다. 시스템의 모든 부분이 같은 저장소에 있으므로 테스트가 더 쉽고 일관적입니다. 각 마이크로 프론트엔드의 최신 코드가 항상 같은 저장소에 있기 때문에, 로컬 실행을 조율해 자동화된 e2e 및 통합 테스트를 실행하기도 수월합니다.

이 자동화 테스트는 모노레포 변경에 의해 트리거되는 CI/CD 파이프라인에서 실행할 수 있습니다. 전체 시스템을 항상 함께 검증하고, 이전에는 찾기 어려웠던 마이크로 프론트엔드 사이의 통합 지점 문제도 더 일찍 발견할 수 있습니다.

테스트 스위트도 실제 사용자가 최종 배포된 애플리케이션을 사용하는 방식에 더 가깝게 작성할 수 있어 제품 품질을 높이는 데 도움이 됩니다.

## Nx는 어떤 역할을 하나요?

Nx는 개발 생산성을 높이고, CI 성능을 최적화하며, 코드 품질을 유지하는 데 필요한 도구와 기법을 제공하는 강력한 오픈소스 빌드 시스템입니다. Monorepo와 특히 잘 어울리며, Angular와 React 프로젝트를 위한 Module Federation 지원을 기본 제공합니다.
