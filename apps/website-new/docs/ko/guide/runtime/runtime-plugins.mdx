# 런타임 플러그인

런타임 플러그인을 사용하면 core runtime 자체를 수정하지 않고도 **런타임 동작**을 바꿀 수 있습니다.

다음과 같은 작업이 필요할 때 사용합니다.

- 런타임에서 remote URL 재작성
- manifest 요청 방식 커스터마이즈
- script 로딩 패치
- shared dependencies 해석 방식 재정의
- 복구 또는 fallback 동작 추가
- 새로운 remote 로딩 방식 도입

빌드 설정에 플러그인 경로만 **등록**하면 되는 경우에는 [`runtimePlugins`](/configure/runtimeplugins.html) 설정을 참고하세요. 전체 hook 목록이 필요하다면 [Runtime Hooks](/guide/runtime/runtime-hooks.html)를 확인하세요.

## 개념

런타임 플러그인은 `ModuleFederationRuntimePlugin`을 반환하는 함수입니다.

```ts
import type { ModuleFederationRuntimePlugin } from '@module-federation/enhanced/runtime';

export default function myRuntimePlugin(): ModuleFederationRuntimePlugin {
  return {
    name: 'my-runtime-plugin',
  };
}
```

함수 형태로 작성하는 이유는 다음과 같습니다.

- 옵션을 받을 수 있습니다.
- closure로 내부 상태를 유지할 수 있습니다.
- 같은 플러그인 로직을 여러 환경에서 재사용할 수 있습니다.

## 플러그인 등록

런타임 플러그인은 세 위치에 등록할 수 있습니다.

1. 빌드 시점: `runtimePlugins`
2. 특정 런타임 인스턴스: `registerPlugins(...)` 또는 `instance.registerPlugins(...)`
3. 전역 런타임: `registerGlobalPlugins(...)`

### 빌드 시점 등록

해당 host에서 플러그인이 항상 필요하다면 빌드 시점에 등록하세요.

```ts title="module-federation.config.ts"
const path = require('path');

export default {
  name: 'host',
  remotes: {
    catalog: 'catalog@https://registry.example.com/mf-manifest.json',
  },
  runtimePlugins: [
    [
      path.resolve(__dirname, './plugins/rewrite-remote-entry.ts'),
      {
        fromHost: 'registry.example.com',
        toHost: 'cdn.example.com',
      },
    ],
  ],
};
```

### 런타임 등록

플러그인이 사용자 상태, 환경, 기능 플래그, 시작 후 가져온 데이터에 따라 달라진다면 런타임에서 등록하세요.

```ts
import { createInstance } from '@module-federation/enhanced/runtime';

import rewriteRemoteEntryPlugin from './plugins/rewrite-remote-entry';

const mf = createInstance({
  name: 'host',
  remotes: [
    {
      name: 'catalog',
      entry: 'https://registry.example.com/mf-manifest.json',
    },
  ],
});

mf.registerPlugins([
  rewriteRemoteEntryPlugin({
    fromHost: 'registry.example.com',
    toHost: 'cdn.example.com',
  }),
]);
```

### 전역 런타임 등록

현재 인스턴스 하나가 아니라 앞으로 만들어질 모든 런타임 인스턴스에서 플러그인을 사용할 수 있게 하려면 `registerGlobalPlugins(...)`를 사용합니다.

공유 instrumentation, 앱 전체 정책, host 기본값처럼 여러 인스턴스에 공통으로 적용해야 하는 동작에 적합합니다.

```ts
import {
  registerGlobalPlugins,
  createInstance,
} from '@module-federation/enhanced/runtime';

import runtimePlugin from './plugins/runtime-plugin';

registerGlobalPlugins([runtimePlugin()]);

const mf = createInstance({
  name: 'host',
  remotes: [
    {
      name: 'catalog',
      entry: 'https://registry.example.com/mf-manifest.json',
    },
  ],
});
```

`registerGlobalPlugins(...)`는 `name` 기준으로 플러그인을 중복 제거합니다. 실제로는 런타임 인스턴스를 만들거나 사용하기 전에 호출해 전역 플러그인이 일관되게 반영되도록 하는 것이 좋습니다.

## 알맞은 hook 고르기

| 작업 | Hook | 언제 사용하나요? |
| --- | --- | --- |
| remote 조회 입력 변경 | `beforeRequest` | remote 해석이 시작되기 전에 요청을 재작성해야 할 때 |
| 해석된 entry URL 재작성 | `afterResolve` | 런타임이 remote를 해석한 뒤 `remoteInfo.entry`를 바꾸고 싶을 때 |
| manifest 네트워크 요청 커스터마이즈 | `fetch` | manifest 로딩에 credentials, header, retry, fallback fetch 동작이 필요할 때 |
| 삽입되는 script/link 커스터마이즈 | `createScript`, `createLink` | `crossorigin`, timeout, custom script/link element가 필요할 때 |
| remote init 전 share scope 조정 | `beforeInitContainer`, `initContainerShareScopeMap` | remote가 초기화될 share scope를 바꾸고 싶을 때 |
| shared dependencies 선택 결과 재정의 | `resolveShare` | 런타임이 선택한 shared 구현 대신 다른 구현을 강제로 사용하고 싶을 때 |
| remote 로드 상태 관찰 | `afterMatchRemote`, `afterLoadRemote` | `loadRemote`의 요청 추적 또는 최종 성공/실패 상태가 필요할 때 |
| shared dependencies 상태 관찰 | `afterLoadShare`, `errorLoadShare` | 누락된 shared dependencies, 버전 불일치, eager 설정 오류를 진단할 때 |
| 로딩 실패 복구 | `errorLoadRemote` | fallback module, 오프라인 동작, 단계별 복구가 필요할 때 |
| 새로운 remote 로딩 전략 구현 | `loadEntry` | remote entry 로딩 방식을 완전히 커스터마이즈하거나 새로운 remote type을 지원할 때 |

## 예제: 해석된 remote entry 재작성

remote가 이미 해석된 뒤, 로딩을 계속하기 전에 최종 URL을 바꾸고 싶다면 `afterResolve`가 적합합니다.

이 패턴은 다음 상황에 유용합니다.

- CDN 우회
- 환경 전환
- registry 기반 라우팅
- domain 정규화

```ts
import type { ModuleFederationRuntimePlugin } from '@module-federation/enhanced/runtime';

interface RewriteRemoteEntryOptions {
  fromHost: string;
  toHost: string;
}

export default function rewriteRemoteEntryPlugin(
  options: RewriteRemoteEntryOptions,
): ModuleFederationRuntimePlugin {
  return {
    name: 'rewrite-remote-entry',
    async afterResolve(args) {
      const entry = args.remoteInfo?.entry;
      if (!entry) {
        return args;
      }

      try {
        const currentUrl = new URL(entry);
        if (currentUrl.hostname !== options.fromHost) {
          return args;
        }

        const nextUrl = new URL(entry);
        nextUrl.hostname = options.toHost;
        args.remoteInfo.entry = nextUrl.toString();
      } catch {
        // Ignore non-URL entries and keep the original resolution.
      }

      return args;
    },
  };
}
```

이 hook을 쓰는 이유는 다음과 같습니다.

- `beforeRequest`는 더 이른 단계라 아직 remote가 해석되지 않았습니다.
- `afterResolve`에서는 이미 `remoteInfo.entry`에 접근할 수 있습니다.
- 여기에서 `args.remoteInfo.entry`를 바꾸면 기존 path, query, hash를 유지한 채 host만 바꿀 수 있습니다.

:::tip 런타임 전용 주의점

`afterResolve`에서 URL을 재작성하면 런타임 로딩 동작만 바뀝니다. 타입 생성이나 빌드 시점 도구가 사용하는 remote URL까지 자동으로 바뀌지는 않습니다. 생성된 remote 타입에 의존한다면 해당 경로도 별도로 맞춰 두세요.

:::

## 예제: manifest fetch 커스터마이즈

manifest 요청 자체에 별도 동작이 필요하다면 `fetch`를 사용하세요.

```ts
import type { ModuleFederationRuntimePlugin } from '@module-federation/enhanced/runtime';

export default function fetchManifestWithCredentials(): ModuleFederationRuntimePlugin {
  return {
    name: 'fetch-manifest-with-credentials',
    fetch(manifestUrl, requestInit, remoteInfo) {
      const headers = new Headers(requestInit?.headers);
      headers.set('x-mf-host', 'host');
      if (remoteInfo?.name) {
        headers.set('x-mf-remote', remoteInfo.name);
      }

      return fetch(manifestUrl, {
        ...requestInit,
        credentials: 'include',
        headers,
      });
    },
  };
}
```

`fetch`는 다음 상황에 사용합니다.

- credentials 설정
- 인증 header 추가
- manifest retry
- 사용자 정의 프록시 로직

이미 준비된 transport policy가 필요하다면 내장 retry 플러그인을 참고하세요.

## 예제: host가 가진 shared dependencies 우선 사용

최종 shared module selection result를 바꾸려면 `resolveShare` hook을 사용합니다.

중요한 점은 `args.scope` 또는 `args.version`만 바꾸는 것으로는 충분하지 않다는 것입니다. 실제 선택 결과를 바꾸려면 `args.resolver`를 교체해야 합니다.

```ts
import type { ModuleFederationRuntimePlugin } from '@module-federation/enhanced/runtime';

export default function preferHostReact(): ModuleFederationRuntimePlugin {
  return {
    name: 'prefer-host-react',
    resolveShare(args) {
      if (args.pkgName !== 'react') {
        return args;
      }

      const hostVersionMap = args.shareScopeMap.default?.react;
      if (!hostVersionMap) {
        return args;
      }

      const preferredShared =
        hostVersionMap[args.version] ?? Object.values(hostVersionMap)[0];
      if (!preferredShared) {
        return args;
      }

      args.resolver = () => ({
        shared: preferredShared,
        useTreesShaking: false,
      });

      return args;
    },
  };
}
```

## 실패 처리와 `shareStrategy`

런타임 fallback은 `errorLoadRemote`에서 처리하는 것이 좋습니다.

한 가지 중요한 점은 `shareStrategy`에 따라 동작 시점이 달라진다는 것입니다.

- `version-first`: 시작 시점에 remote entry를 미리 로드해 shared dependencies를 초기화합니다.
- `loaded-first`: 실제로 remote가 사용될 때까지 로딩을 미룹니다.

따라서 다음 차이가 생깁니다.

- `version-first`에서는 오프라인 remote가 `lifecycle: 'beforeLoadShare'` 단계에서 일찍 실패할 수 있습니다.
- `loaded-first`에서는 같은 remote라도 실제 코드가 그것을 사용할 때 더 늦게 실패하는 경우가 많습니다.

remote가 간헐적으로 사용할 수 없는 상태가 될 수 있다면 `errorLoadRemote`와 의도적인 `shareStrategy`를 함께 설계하세요.

## 버전에 민감한 hook

고급 hook은 시간이 지나면서 바뀔 수 있습니다. `afterResolve`, `fetch`, `createScript`, `loadEntry`처럼 자주 쓰는 hook이라도 새로운 인자나 동작에 의존한다면 설치된 런타임 타입을 확인하는 것이 좋습니다.

특히 다음을 사용할 때 중요합니다.

- `createScript`의 추가 script attribute
- `fetch` 또는 `loadEntry`로 전달되는 loader hook 세부 정보
- 내장 플러그인이 사용하는 비교적 드문 lifecycle hook
